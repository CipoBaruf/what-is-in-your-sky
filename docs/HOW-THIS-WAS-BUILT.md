# How this was built

This app was written by Claude Code sessions, one per task, each in its own git worktree,
driven by a script in this repository. Nothing here is a prompt log: the interesting part
is the paperwork the sessions were given and the evidence they left behind, and both are
in the tree. This page is the reading order.

Read it in this order and the workflow explains itself in about twenty minutes.

## 1. [SPEC.md](../SPEC.md) — what the product does

1053 lines. Numbered requirements (`FR-PASS-3`, `FR-LIVE-6`), user stories with acceptance
criteria, a findings table, and a Decision Log that is fixed once written. **Written by
hand**, with the `sdd-spec` skill below, in a conversation with the owner: the owner
answers scope questions one at a time and the session writes the requirement. Every
`FR-` id here is the thing a later session's tests have to point at, so a change to the
product starts on this page and nowhere else.

## 2. [PLAN.md](../PLAN.md) — how it is built

1846 lines. Architecture, the data model, the Web Worker message contract, the testing
strategy, the bundle budgets, and §16 — how the tasks are delivered. **Written by hand**
in the same way, one section per question the spec left to engineering. Its Decision Log
(`D-1` … `D-375`) is the other half of the paperwork: a decision records the question, the
answer and what was given up, so a later session that disagrees has to argue with a
written reason rather than with a silence.

The section to read is [§16, Delivery](../PLAN.md#16-delivery-of-the-v1-and-v11-tasks-v1-11-v11-9):
lanes (which files a task may touch), waves (which tasks can run at once), the merge
policy, and the model policy.

## 3. [TASKS.md](../TASKS.md) — the ordered slices

1459 lines, one entry per task: a goal, the requirement ids it satisfies, its lane, its
dependencies, its scope, a *done when* list, and — once it is merged — a **Done** note.
**Generated by a session** from the two documents above with the `sdd-breakdown` skill,
and never edited by hand except to check a task off. The **Done** notes are written by the
implementing session at the end of its own run; they are where a task says what it did
differently from what it was asked, and they are the most honest thing in the repository.

## 4. [scripts/sdd-run.ts](../scripts/sdd-run.ts) — the driver

393 lines, plus [scripts/sdd/](../scripts/sdd/) beside it. **Written outside the task
loop**, as a direct commit on `main` from PLAN §16.4, and then amended by the decisions it
ran into: `D-89` (a headless session commits as it goes, because a session that commits
once at the end turns any limit into total loss), `D-131` (a per-task model override),
`D-132` (waves run concurrently, capped at three, one task per lane). It reads `TASKS.md`,
works out which tasks are ready, and for each one:

1. makes a worktree and a branch off `origin/main`, installs the dependencies;
2. writes `sdd-run/<id>.brief.md` — the task's entry plus every requirement, story,
   finding and decision that entry names, so the implementing session never reads the
   three documents in full;
3. runs a headless Claude Code session on the brief, with a tool allowlist that cannot
   push and cannot call `gh`;
4. checks the branch has commits, rebases, pushes, opens a pull request and waits for CI;
5. runs a **second** session — a different context, sometimes a different model — whose
   only job is to review the diff and write its findings to a JSON file, which the driver
   posts on the pull request;
6. merges when the task's gate says `auto`, and stops for the owner when it says `owner`.

`npm run sdd -- --status` prints where every task stands. The driver is why the sessions
run in parallel without stepping on each other, and the lanes in PLAN §16.1 are why two
sessions editing at the same time do not collide.

## 5. One task, end to end: R28

The clearest way to see the loop is to follow a single task through it.

- **The entry:** [R28 in TASKS.md](../TASKS.md) — *Install hint, update banner and the
  favourites list*. Goal, `FR-OFF-6` and `FR-OFF-1`, three dependencies, a scope naming the
  components, a *done when* list of five items, and the lane crossings declared up front.
  Written by the breakdown session.
- **The branch and the pull request:**
  [#54](https://github.com/CipoBaruf/what-is-in-your-sky/pull/54), opened by the driver
  from what the implementing session committed. Its body is the summary that session wrote
  to `sdd-run/R28.summary.md`.
- **The review session's findings:** posted on that pull request as a comment headed
  *Automated review (PLAN §16.4)* —
  [the conversation](https://github.com/CipoBaruf/what-is-in-your-sky/pull/54). It found
  five things, which became `F-29` … `F-33` in
  [the findings table in SPEC §4.20](../SPEC.md): a saved place that does not reseed
  the coordinates field, an update offer still reachable under an open pass, an install
  listener that only exists while the shell is mounted, an uncaught `prompt()` rejection,
  and an e2e assertion that ran before hydration and passed without the guard it was
  testing. None of them were fixed on that branch. Findings become their own later task —
  `R49` was one — so the merge is not held open while a session argues with its reviewer.
- **The captures:** the session's own evidence, at 390 px in both languages —
  [the favourites list](screenshots/r28-favourites-390-dark-en.png),
  [the same list in Spanish](screenshots/r28-favourites-390-dark-es.png),
  [the install hint](screenshots/r28-install-390-dark-en.png),
  [its iOS branch](screenshots/r28-install-ios-390-dark-en.png),
  [the update banner](screenshots/r28-update-390-dark-en.png).
- **The Done note:** written back into the R28 entry when it merged. Read the last
  paragraph of it: two of the five things it records were caught by the tests rather than
  by the review, and it says which.

## 6. [The four skills](../.claude/skills/) — what the sessions were told

Small Markdown files, **written by hand**, that a session loads by name. They are the
whole of the process instruction; there is no hidden prompt.

- [`sdd-spec`](../.claude/skills/sdd-spec/SKILL.md) — revise SPEC.md and then PLAN.md for a
  new phase or a scope change. Asks the owner one question at a time.
- [`sdd-breakdown`](../.claude/skills/sdd-breakdown/SKILL.md) — regenerate TASKS.md as
  vertical slices, with what each entry must carry.
- [`sdd-implement`](../.claude/skills/sdd-implement/SKILL.md) — the task loop: read the
  brief, branch, test each acceptance criterion, commit in small steps, check the task off,
  write the summary. It is 33 lines.
- [`visual-review`](../.claude/skills/visual-review/SKILL.md) — capture a task's screens at
  390 px and 1280 px, in both languages and both themes, and file them under
  `docs/screenshots/`.

## Why `docs/` is 53 MB

35 MB of it is [`docs/screenshots/`](screenshots/), 326 PNGs. They are not decoration.
Each phase's definition of done requires a capture set shot from the release build in both
languages and both themes (`FR-COMP-6`, `D-179`), and
[`tests/docs/captures.test.ts`](../tests/docs/captures.test.ts) fails if a file the set
names is missing or a file it does not name has appeared. That is the acceptance evidence
for every screen in the app, held in the repository at the commit it was shot from, which
is the only place it can be checked against later. The rest is
[`docs/mockups/`](mockups/) and two spike reports.

The app itself is well under a megabyte; nothing in `docs/` reaches the bundle.
